# Build and dependency modernization plan

Draft based on repository inspection and local diagnostics on 2026-09-10. This proposes implementation work; it does not change the application's tooling or dependencies.

The priority is to make installation reproducible, give generated dependencies a stable interface, and make validation trustworthy. Once those boundaries exist, changing package managers, moving the server, and replacing webpack become manageable, separate changes.

## Recommended destination

| Area | Recommendation | Timing |
| --- | --- | --- |
| Package manager | npm, one committed application `package-lock.json`, `npm ci` in CI | Early, after eliminating generated-package and Yarn lifecycle prerequisites |
| Server runtime | A pinned, supported Node 24 LTS release and npm version | Early; keep the legacy compiler toolchain isolated if necessary |
| Server source | TypeScript in `server/`, compiled with `tsc` to `dist/server/` | Early, incrementally |
| Browser build | Vite with React integration, producing `dist/client/` | After artifact and package interfaces are stable |
| Tests | Vitest for unit/integration tests; browser smoke tests for workers and simulation | Before the browser bundler switch |
| Code quality | ESLint for correctness, Prettier for formatting, explicit TypeScript checks | Early |
| Styling | Ordinary CSS/CSS Modules with CSS custom properties for themes | Gradual, independent of build migration |
| Bun | Optional package-manager experiment, then a separate runtime experiment | Last; neither is needed to solve the current problems |

Use a single application package initially. A server directory does not require a monorepo or a server bundler. Add npm workspaces only if independently packaged components or production dependency isolation justify them.

Node 20 in the current Dockerfile is now EOL; Node's release schedule identifies Node 24 as LTS. Pin an actual patch release and container digest during implementation. [Node release schedule](https://nodejs.org/en/about/previous-releases).

## What is actually wrong today

### Installation is coupled to generating dependencies

[`package.json`](package.json) makes `build-deps` run the Python builder and then `yarn add file:dependencies/kipr-scratch/kipr-scratch`. That package's manifest is itself generated by the Scratch packaging script. A fresh checkout therefore lacks a dependency that the application installer needs. `yarn add` also combines building with dependency resolution and potential manifest/lockfile updates.

[`dependencies/build.py`](dependencies/build.py) installs and activates Emscripten 3.1.19, builds libkipr for C, builds patched CPython, builds libkipr's Python binding, generates documentation, builds/packages Scratch, and generates the graphical runtime. This is a real native toolchain, not simply an unusually long JavaScript installation.

The nested Scratch build runs its own `npm install`, uses webpack 4, enables `--openssl-legacy-provider` on newer Node versions, and modifies its source checkout. Its generated package always has version `1.0.0`, regardless of content. The CPython patch subprocess does not check its return code. The dependency manifest contains absolute build-machine paths, and its directory fingerprints use Python's process-randomized `hash()`, including generated tree contents. Those fingerprints are unsuitable as reproducible artifact identities.

The generated manifest also selects the first directory under `emsdk/node` rather than explicitly selecting the activated SDK's Node executable. Native build subprocesses receive a very limited replacement environment. These are sources of machine-dependent behavior to remove deliberately.

### The JavaScript dependency graph is not an accurate contract

- The manifest selects IvyGate commit `6ef276e…`; `yarn.lock` contains an IvyGate entry for `5529f4e…`. Reconcile the intended source before converting the lockfile.
- The installed IvyGate package has `prepare: yarn run build`. Removing Yarn from root scripts alone still leaves installation dependent on Yarn. Verify this behavior against the chosen IvyGate commit because the current manifest, lockfile, and installation are not aligned.
- `itch` uses the Git ref `#36`. The lock resolves it to a full commit, but refreshing that ref is another source of drift. Prefer immutable built releases.
- Server files directly require `express`, but it is absent from direct dependencies. It currently resolves from the installed transitive graph. `terser-webpack-plugin` is also required directly by build configuration without being directly declared.
- The webpack SCSS rule references an undeclared `sass-loader`; either remove the unused rule or declare and support the actual Sass pipeline.
- Build loaders live in runtime `dependencies`. The root Yarn `resolutions` entry needs an explicit npm migration decision.
- Browser code imports dependency internals such as `itch/src/…` and `ivygate/dist/src`. The application build includes special handling for TypeScript in dependencies.

### Passing CI does not establish type correctness or runtime parity

Local checks against the existing installation:

| Check | Observed result |
| --- | --- |
| ESLint, matching the root lint script | Passed: 592 files, zero reported errors or warnings |
| Jest, serial execution without its cache | Passed: 4 suites, 9 tests |
| `tsc --noEmit --pretty false` | Failed: 9 parse diagnostics in `@types/d3-dispatch` |
| Production webpack compilation, with emission disabled | Completed in about 57 seconds; no webpack errors or warnings; Babel printed two large-file notices |

The production diagnostic compiled and optimized the application but deliberately skipped file emission and the `afterEmit` declaration-generation plugin, preserving the existing `dist`. It is not a full `yarn build` verification. Babel reported code-generator formatting deoptimization for Monaco's TypeScript worker and generated `python.js`, both over 500 KB; those notices do not by themselves demonstrate runtime slowdown. The broader native/bootstrap warning inventory still needs a clean builder run. Prefer limiting unnecessary transforms on generated assets and measuring their delivered sizes over merely hiding the notices.

Installed TypeScript is 4.9.5; the declarations use syntax it cannot parse. `skipLibCheck` does not fix a parser incompatibility. Installed `@types/node` is 25.9.3 while the local runtime is Node 20.20.2, illustrating another boundary that needs explicit version ownership.

Webpack uses `ts-loader` with `transpileOnly: true`; it also runs a declaration-generation plugin, but CI has no explicit standalone typecheck gate. The root `types` array is outside `compilerOptions`, test inclusion is inconsistent, and the i18n config combines CommonJS output with `NodeNext` resolution. Fix the compiler/configuration compatibility first, then measure the application type errors currently hidden behind it.

There are two ESLint configurations. The installed ESLint 7 uses `.eslintrc.js`; `eslint.config.mjs` imports undeclared configuration packages and contains an absolute developer-machine path. Both contain formatting rules, and both exclude tests, tooling, and i18n from their intended coverage. The successful lint run does not validate a future flat-config setup.

### Build and deployment responsibilities are mixed

[`configs/webpack/common.js`](configs/webpack/common.js) handles four HTML pages, Monaco workers, simulator workers, generated documentation/translations, CPython module resolution, asset conversion, and declaration generation. It also defines `watchOptions` twice, silently replacing the earlier object. Production excludes the Monaco chunk from Terser and disables webpack performance hints globally.

The checked-in application pipeline is webpack/Babel/ts-loader/Terser. I did not find a separate application esbuild configuration or direct dependency. Vite migration should be scoped to the actual webpack responsibilities. Current Vite 8 uses Rolldown/Oxc, so older descriptions of Vite as an esbuild/Rollup combination are no longer an accurate migration target. [Vite 8 announcement](https://vite.dev/blog/announcing-vite8).

The single-stage [`Dockerfile`](Dockerfile) installs system tools and Yarn, copies the whole checkout, then builds everything. CI does not select a Node version or use a frozen install; deployment workflows use old action versions and `::set-output`. The pull-request checkout does not request LFS, while staging does. `start-prod` rebuilds the browser application each time it starts.

Crucially, [`express.js`](express.js) invokes `emcc`/`em++` for C/C++ requests at runtime. A smaller container must retain the compiler, its supported runtime dependencies, headers, libraries, and writable working/cache directories unless compilation becomes a separate service. Python runs in a browser worker but still needs the served CPython and libkipr artifacts.

First PR: document and stabilize the existing system before broad upgrades.

1. Resolve the IvyGate manifest/lock mismatch against intended application behavior and record exact dependency/submodule commits. Inventory installed, locked, and requested versions separately.
2. Add missing direct runtime/build dependencies using compatible existing versions. Mark the application private if it is not intended for npm publication; verify whether anyone consumes the generated `simulator.d.ts` before removing it.
3. Select supported Node/npm versions for local development, CI, and the application container. Validate the legacy native builder separately; if it needs an older environment temporarily, pin that environment explicitly.
4. Capture cold/warm install and build time, peak memory, bundle sizes, warning categories, and image size from a clean disposable checkout. Record behavior on the actual supported browsers and deployment platform.
5. Inventory vulnerabilities and deprecations from the resolved graph, including Git packages, the nested Scratch graph, native artifacts, and the container. Classify runtime exposure separately from build-only dependencies; use the findings to accelerate urgent fixes ahead of the broader sequence.
6. Add a small browser smoke baseline for C, C++, Python, and graphical programs: start, output, robot movement, stop, and restart. Cover invalid compiler input as well as success. Include login, an authenticated API request, the LMS plugin, parental-consent routing, and page reloads at deep links.

Completion: a documented reproducible baseline, known failures with owners, and smoke coverage for the features most likely to break. Do not interpret the existing 9 unit tests as simulation or server coverage. Temporary warning/error exceptions must identify a specific cause and removal condition; prevent new problems while retiring the existing ones.

## Stage 1 — Separate artifact production from artifact consumption

This is the most valuable change and the prerequisite for an ordinary `npm ci` workflow.

Create explicit artifact contracts:

| Artifact | Contents | Consumers |
| --- | --- | --- |
| Scratch distribution | Installable built JavaScript and media with a real immutable version | Browser build and static server |
| Browser runtime bundle | CPython JS/Wasm/data, libkipr Python binding, graphical runtime, generated documentation | Browser build and static server |
| Compiler distribution/image | Compatible Emscripten toolchain, required executables, sysroot, libkipr headers/libraries | Server-side C/C++ compiler |

Build these in a dedicated pinned builder, initially preserving the existing Emscripten/CPython/libkipr versions. Publish Scratch as an ordinary prebuilt package or immutable tarball. Publish the other artifacts with checksums and a manifest describing the complete compatible set. A registry is convenient, but a checksummed release archive works too; source checkouts must no longer be prerequisites for installing the application.

Use a content identity derived from submodule commits, patch bytes, toolchain versions, build flags, target platform, and recipe version. Use deterministic SHA-256 hashing of named, sorted inputs. Include transitive native inputs and regenerate dependent artifacts when any ABI-affecting input changes. Cache by that identity, verify downloaded contents, and test cold-cache rebuilds. Caches accelerate the build; retained immutable releases supply the dependency.

Make manifests relocatable: artifact-relative paths plus a configured artifact root. Native compiler distributions also need a supported installation path/layout; use a fixed container prefix initially if necessary and prove relocation before promising it. Include source provenance and the applicable license/source materials with distributed artifacts.

Split the current builder into separately invocable steps with explicit inputs/outputs. Reuse the Python code where practical. Check every subprocess result, handle already-applied patches separately from failed patches, patch temporary source copies, select exact tool executables, and build out of tree. Repeated builds should not dirty submodules or change tracked manifests. Documentation generation should not force every application developer to install Doxygen and SWIG.

Give IvyGate and Itch the same package discipline: built JS, declarations, public exports, exact versions, and validated peer dependencies. Remove Yarn-dependent consumer lifecycle scripts. Migrate deep imports to supported exports, including compatibility subpath exports where useful. Check package tarball contents in a small consumer project; a successful build inside the source repository is insufficient.

Future commands should have clear meanings:

```text
npm ci                    install application packages from the lockfile
npm run deps:fetch        acquire and verify the pinned runtime artifacts
npm run deps:build        explicitly rebuild artifacts from pinned sources
npm run deps:verify       validate versions, contents, and expected paths
npm run build            generate i18n and build client/server
npm start                run the already-built server
```

`deps:fetch` must work after a normal install using checked-in tooling. No `preinstall` hook or hidden native compilation should recreate the dependency cycle. Preserve `build-deps` temporarily as a documented compatibility command if helpful, but remove its package-manifest mutation.

Completion: a fresh app checkout installs without native tools, generated package directories, Yarn, or initialized native submodules. Fetching the pinned artifacts enables the full build. Building those artifacts from source remains documented and supported.

## Stage 2 — Migrate to npm and finish install reproducibility

1. Convert the reconciled dependency graph to `package-lock.json` using the selected npm version. npm can use a Yarn lock during installation, but inspect the resulting graph; different peer resolution and the existing mismatch preclude assuming an identical tree. [npm install](https://docs.npmjs.com/cli/install/).
2. Replace all application Yarn invocations in scripts, README, CI, and Docker. Check upstream package lifecycle scripts and builder tooling too. Remove unused scripts pointing at the absent `scripts/install-ngrok.sh` and `scripts/share-ngrok.sh`, or implement them only if those workflows are still wanted.
3. Translate the React type resolution into a compatible direct version and/or valid root npm `overrides`. Direct-dependency override rules differ from Yarn resolutions; a blind field rename can fail. Align React/React DOM types with their runtime and declare `@types/node` for the supported Node major. [npm package metadata and overrides](https://docs.npmjs.com/cli/v11/configuring-npm/package-json/).
4. Resolve peer conflicts explicitly, especially IvyGate's React/Redux/Styletron ecosystem. Avoid making `--force` or `--legacy-peer-deps` the normal installation policy.
5. Use `npm ci` in automation, with the lockfile committed. Install must leave manifests and lockfiles unchanged. Validate on a clean machine with no global Yarn and no existing `node_modules`. [npm ci](https://docs.npmjs.com/cli/commands/npm-ci/).
6. Retire the root `yarn.lock` and `.yarncache` configuration together. The isolated Scratch source builder may retain its own npm lockfile; it is a separate build context, not a competing application lockfile.

Completion: one supported application installer and lockfile, no undeclared imports, and repeatable clean installs. Keep dependency major upgrades out of this conversion except where needed to repair incompatible resolution.

## Stage 3 — Make quality checks meaningful; adopt Vitest

Upgrade TypeScript and typescript-eslint/ESLint as a tested compatible group. Choose supported releases at implementation time; the goal is a coherent matrix rather than independently selecting every newest major.

Split configuration into browser, server, tooling/i18n, and tests. Browser code uses DOM libraries; server code uses Node libraries; worker code gets the appropriate worker globals. Move `types` into `compilerOptions`, fix i18n's module/resolution pairing, and include all intended tests. Keep browser transpilation separate from `tsc --noEmit`; Vite likewise does not typecheck during normal transforms. [Vite TypeScript support](https://vite.dev/guide/features).

Resolve declaration parser incompatibilities first, then actual type errors. Do not conceal the backlog with blanket `any`, `@ts-nocheck`, or permanent exclusions. Establish strict checking for new server code; increase browser strictness in focused steps with a shrinking, explicit backlog if needed.

Replace both ESLint configurations with one portable flat configuration. Cover maintained client, server, tests, and tooling, and ignore generated/vendor output. Enable correctness rules suited to each environment, including promise handling and React hooks checks. Remove stylistic rules. Add Prettier and `eslint-config-prettier`; run formatting independently, avoiding a formatting plugin that reports every Prettier difference as a lint failure. [Prettier's integration guidance](https://prettier.io/docs/integrating-with-linters.html).

Use a separate formatting-only commit and, if formatting broadly, record it in `.git-blame-ignore-revs`. Preserve existing quote/indentation conventions where sensible and exclude generated translations, vendored JS, and native source submodules. CI should expose separate `lint`, `format:check`, and `typecheck` commands.

Adopt Vitest while webpack still builds the browser application. Use a standalone test config sharing aliases and safe build constants, not importing the entire production build configuration. Port the four existing suites, initialize the i18n test global, replace the ScriptManager suite's `jest.mock` calls, and inspect ESM/mock-hoisting behavior. Keep tests in the Node environment unless they actually require a DOM. Babylon ESM handling should be verified with the Scene and ScriptManager tests. [Migrating from Jest](https://vitest.dev/guide/migration/jest).

Run both runners temporarily to establish parity, then remove Jest, ts-jest, and Jest-only types/configuration. `npm test` should run once in CI; provide `test:watch` for interactive use. Vitest is not a substitute for the browser worker/Wasm tests or standalone typechecking.

Completion: the existing four suites and nine tests pass with Vitest, typecheck failures are visible and addressed under an explicit policy, and formatting/correctness checks have distinct responsibilities. Test names/counts should be compared to avoid silently losing coverage during migration.

## Stage 4 — Move the server into TypeScript

Use this layout while retaining `src/` for the browser application:

```text
src/                      existing browser application
server/
  app.ts                  createApp(config, services), no listening on import
  index.ts                configuration, service setup, listen/shutdown
  config.ts               validated configuration and artifact paths
  routes/                 existing routers moved incrementally
  services/               compiler, Firebase, mail, logging, metrics
test/                     unit, server integration, browser smoke tests
tooling/                  build and artifact commands
dist/
  client/
  server/
```

Move files first with path corrections and behavioral tests; then convert a few modules at a time. `allowJs` can support a temporary mixed tree. Initially retain CommonJS-compatible server output to avoid coupling the move to Express and ESM dependency upgrades. Use a deliberate Node module/resolution configuration, compile with `tsc`, and execute emitted JavaScript in production. A development TS runner/watch process is optional convenience.

Move all server modules, including `ai/` and the existing routers. Determine whether `projects/projects.js` is live before moving or removing it. Give HTTP request augmentation and configuration concrete types; validate external inputs at runtime because TypeScript alone does not validate requests or environment variables.

Replace working-directory and `__dirname` assumptions with explicit client/static/artifact locations. Correct `logger.js`'s package-version lookup when it moves. Extract compiler invocation behind an injected interface, allowing request/response tests without building C during every unit test. Keep a real compile smoke test against the production compiler distribution.

Protect routing and middleware behavior: API proxy ordering, auth, sessions/CSRF, rate limiting, metrics, login, LMS, consent paths, and SPA fallback. Consolidate duplicate graphical static routes under tests. When upgrading Express separately, account for changes to wildcard route syntax such as `/parental-consent/*` and `*`.

Separate `build`, `dev`, and `start`; starting production must not rebuild. Ensure cleaning `dist/client` cannot delete `dist/server`. No Firebase credentials or network calls should be required merely to import `createApp` for a test.

Completion: server source lives under `server/`, new TS code is checked, compiled output starts from a supported working directory, and HTTP integration plus real compiler smoke tests pass.

## Independent track — Retire Styletron gradually

Styletron appears in 193 application source files. IvyGate also depends on it and expects compatible peer packages, so this is a component migration plus an upstream dependency change.

Start with new components and leaf UI elements. Use plain CSS for resets, global styles, and theme tokens; prefer CSS Modules for component scoping. Represent themes with CSS custom properties, discrete states with classes/data attributes, and truly dynamic numeric values with inline custom properties. Preserve responsive rules, pseudo selectors, portal styling, and theme changes.

Then migrate shared interface primitives and their callers, replacing `styled`, `withStyleDeep`, and Styletron component types incrementally. Both systems can coexist during migration. Add focused visual comparisons for affected screens in supported themes and viewport sizes. Check all four entry points' providers.

Completion: remove Styletron dependencies/providers only after neither application code nor the chosen IvyGate release requires them. This work need not delay npm, TypeScript server, Vitest, or Vite adoption.

## Optional final track — Evaluate Bun on evidence

Use npm as the supported baseline first. Later test Bun installation in an isolated branch against the same dependency versions: lifecycle behavior, peer resolution, package contents, platform-specific tooling, install speed, CI caching, and reproducibility. Avoid maintaining competing authoritative lockfiles in the main workflow.

Treat Bun's runtime as a separate experiment. Measure representative server requests and concurrent compiler jobs, and test Firebase/network behavior, sessions/proxying, streams, child-process errors/timeouts, logging/metrics, signals, and shutdown. Bun documents Node compatibility by API; compatibility should be proven for this server's paths. [Bun Node compatibility](https://bun.sh/docs/runtime/nodejs-compat).

Keep Node unless the experiment produces a worthwhile benefit. Emscripten itself may still require its own supported Node executable even if the application eventually runs on Bun.

## Delivery order and safeguards

Implement the stages as multiple reviewable PRs, not one conversion branch:

1. Baseline evidence, manifest/lock repair, missing direct dependencies, supported runtime selection, and smoke harness.
2. Deterministic artifact builder and manifest; prebuilt Scratch/IvyGate/Itch package interfaces; ordinary artifact fetching.
3. npm conversion across application scripts, CI, documentation, and Docker.
4. Compatible TypeScript/compiler configuration; ESLint/Prettier split; separate mechanical formatting commit.
5. Vitest parity and server integration coverage.
6. Server directory move and incremental TypeScript conversion.
7. Vite prototype, worker/runtime compatibility adapters, parity verification, then webpack removal.
8. Remaining dependency-family upgrades and final container/CI simplification, followed by native-toolchain upgrades.
9. CSS component migrations independently; Bun experiments only after the baseline is stable.

Upgrade urgency can change this order, but keep runtime, package-manager, bundler, and framework changes independently diagnosable. Retain old immutable artifact sets and deployment image digests for rollback. During the Vite trial, keep both build commands; after cutover, roll back by reverting the cutover or deploying the previous image rather than maintaining two permanent pipelines.

Set ongoing maintenance rules: automated dependency PRs grouped by ecosystem, separate native-artifact updates, scheduled cold-cache builds, explicit peer/engine checks, and warning exceptions with an owner and removal condition. Track install/build duration, memory, bundle size, and image size so regressions become visible. Do not use blanket warning suppression or force upgrades to make dashboards green.

The first useful milestone is a clean checkout that runs `npm ci`, fetches pinned artifacts, passes explicit checks, and builds the application without changing dependency manifests or source submodules. That removes the installation trap before the larger technology migrations begin.

## Scope and verification limits

The local test/lint/typecheck results above use the pre-existing installation, not a newly reconciled lockfile. The working tree already contained modified CPython/Scratch submodules and an untracked `.serena/` directory. They were preserved. No install, native rebuild, dependency upgrade, deployment, or external package publication was performed. A fresh vulnerability audit and supported-platform matrix remain Stage 0 work; package age alone is not evidence of a specific vulnerability.
